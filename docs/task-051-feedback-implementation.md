승인 데모 `docs/demo/task-051-feedback-recall-v5.html` (v5) · 사용자 명시 지시에 따른 실제 화면 구현 GO · Designer 최종 인계.

기준 SHA-256 `913af5af374273664c38a055c3b0751f850c895fa752e7f924b27020178d0a20`. 이번 작성 시 선택한 v5 파일만 해시를 계산하여 전달받은 값과 일치를 확인했다. v1~v4는 구현 기준이 아니다. 사용자 후속 요구인 **관장과 보완한 내용을 교정 포인트와 연습 방법에 통합 정리**를 아래 실제 CLI 계약에 포함한다. 최신 사용자 지시 “그럼 같은 승인 요청은 더 하지 말고, 이미 승인한 v5 기준으로 실제 화면 구현을 계속 진행해줘. 내부 기록 문제는 알아서 처리해줘.”와 Leader의 frontend 전체 GO에 따라 이 가이드를 인계한다. 같은 승인을 다시 요청하지 않는다. 아래 API/DTO는 task-051의 최신 확정 계약에 맞췄다.

기록 도구의 기계적 BLOCKED/receipt 부재는 task 기록에 남아 있다. 이를 PASS로 바꾸어 주장하거나 승인 증거를 대리 생성하지 않는다. 이번 작업의 명시적 진행 지시를 다른 task의 게이트 완화로 확대하지 않는다. 독립 Reviewer/QA, 운영 DB 마이그레이션과 배포의 별도 경계는 유지한다.

## 1. 레이아웃 설계

목표는 수업·스파링·영상 복기·개인 연습·기술토론에서 얻은 내용을 독립 피드백으로 보관하고, 관장이 부족한 내용을 한 번에 하나씩 물어 교정점·연습 방법·적용 기준을 완성하는 것이다.

- 홈의 오늘 수업 카드 밖에 별도 `피드백` 카드와 `피드백 추가` 진입점을 둔다.
- 수업 화면 공통 헤더의 우측 버튼은 `+수업`, `+피드백` 순서로 나란히 둔다. `+수업`은 기존 `setEditingClass('new')` 동작을 유지한다. 캘린더/수업목록 본문과 기존 수업·스파링 편집기를 교체하지 않는다.
- 수업 헤더에서 피드백을 열어도 기본값은 오늘 날짜와 빈 상황·기술·내용이다. 수업 ID·선택 날짜·기술을 등록 데이터로 전달하지 않는다. 호출 화면은 닫기 시 복귀용 UI 상태로만 보관한다.
- 복기의 기간 선택은 `전체 / 주 / 월 / 직접선택`. 기본은 현재 달의 달력 월, 주는 월요일~일요일이다. 선택 기간을 피드백·기존 실패·연습 근거와 요약에 함께 적용한다.
- 대표 폭 390px, 경계 360/412px. 함수형 React 컴포넌트와 기존 Card/Button/Icon/Modal을 사용한다. 헤더 버튼·페이지 이동·질문 이동은 44px 터치 영역과 focus-visible을 확보한다.
- 앱 화면의 스크롤은 패널당 한 곳. 공용 영상 상세가 열리는 동안 배경 스크롤·입력은 멈추고 닫으면 카드 스크롤과 트리거 포커스를 복원한다.

## 2. 화면·컴포넌트 구조

### FeedbackPanel

`입력 → 관장과 보완 → 정리 카드`의 흐름을 관리한다. 기존 Layout의 관장실과 독립된 피드백 문맥을 보관하고, 같은 자료를 일반 관장실의 현재 대화로 잘못 연결하지 않는다.

입력 단계는 날짜(필수, 오늘 기본), 상황(자유 입력·선택), 기술(선택), 원문(필수), 영상 연결(선택)으로 구성한다. 상황 예시는 수업·스파링·영상 복기·개인 연습·기술토론·기타이며 자유 입력을 제한하지 않는다. 말해준 사람과 포지션 입력은 없다. 기술 미정 상태도 저장·질문·정리가 가능하다.

데모의 `예시 불러오기`와 합성 영상·기록은 검토 장치다. 실제 서비스에는 데모 데이터를 넣지 않는다.

대화 단계는 현재 질문 하나, 답변 입력, `이전 질문`, `답하고 이어가기`, `확인 대기로 남기고 이어가기`, `지금까지 정리`, `보완 중 저장하고 닫기`를 보여준다. 질문 번호만 표시하고 전체 질문 수나 고정 질문 진행 점은 두지 않는다.

- 이미 상황·기술·행동·관찰 기준이 입력/활성 답변에 있으면 같은 내용을 다시 묻지 않는다.
- 관장이 정리할 만큼 정보가 있다고 판단하면 정리 제안을 표시한다. 사용자는 그 전에 `지금까지 정리`할 수도 있고, 제안 이후 `더 질문받기`를 선택할 수도 있다.
- 이전 질문으로 이동할 때 미제출 답변을 보관한다. 같은 답변으로 앞으로 가면 기존 후속 질문/답변을 재사용한다.
- 이전 답변을 제출해 변경하면 이전 경로를 별도 이력으로 보존하고 활성 후속 질문을 다시 생성한다. 변경 안내와 옛 경로 보기 기능을 제공한다.
- 원문·상황·기술 수정은 활성 대화를 초기화하고 이전 답변을 현재 근거로 사용하지 않는다. 저장된 과거 내용의 보존 정책과 확인 UI는 Backend/Leader가 확정한 revision 계약에 따른다.

정리 카드는 원문, 관장과 확인한 활성 질문/답변, 통합 교정 포인트, 상황별 대응/연결, 연습 방법, 다음 훈련 관찰 기준, 추가 확인 사항, 연결 영상을 보여준다. 질문의 답변을 원문 아래 나열하는 것으로 통합 정리를 대신하지 않는다. 예를 들어 사용자가 다리깃 의미를 보완하면 그 정보가 관련 교정점과 연습법의 문장에도 반영되어야 한다.

### FeedbackClipPicker

기존 ClipsPage의 데이터·필터 동작을 재사용한다. 별도의 유사 검색·집계 규칙을 만들지 않는다.

1. 제목·기술명·설명·태그 검색은 NFC 정규화 후 비교한다.
2. `전체 / 최신순 / 즐겨찾기 / 고정 / 안 써본 것 / 많이 쓴 순`을 제공한다. 안 써본 것은 조회 수가 아닌 드릴+포지션 스파링+스파링 사용 합계 0이다. 최신순은 기존 고정 우선 동작을 유지한다.
3. 기술 선택 드롭다운은 내부 기술 검색과 `모든 기술`을 포함한다.
4. **필터 적용 후** 페이지 크기 5. 결과가 5개를 초과하면 이전/다음·현재/전체 페이지·조회 범위를 보여준다. 정확히 5개면 한 페이지다.
5. 검색/필터/기술 변경 시 1페이지로 돌아가고 결과 축소 시 유효 페이지로 보정한다. 필터나 페이지에 숨은 선택 영상도 유지하며 총 선택 수와 선택 목록을 보여준다.
6. 입력 단계의 접힌 영상 선택 영역은 선택·검색·필터·페이지 이동 중 열린 상태를 유지한다.

영상 데이터 정본은 기존 클립 캐시/조회 API다. 선택은 `clipId`로 저장한다. 제목·URL을 모델이 새로 만들어 연결하지 않는다. 삭제·소유권 변경 등으로 조회할 수 없는 영상은 연결 불가 상태를 표시하고, 다른 사용자의 영상은 반환하거나 저장하지 않는다.

### 공용 영상 상세

`ClipDetailModal`을 직접 사용한다. 피드백 전용 영상 페이지나 복제 모달을 만들지 않는다. `onEdit`, `onDelete`는 전달하지 않는다. 플레이어, 기술/영상 포지션/플랫폼 태그, 설명, 조회·드릴·포지션·스파링 횟수, 연계 기술은 공용 컴포넌트의 동작과 API를 따른다.

열기 전 목록의 검색·필터·페이지·선택·스크롤을 유지한다. 닫기/Escape/배경 클릭으로 복귀한다. 포커스 트랩과 배경 비활성화는 공용 Modal의 지원 상태를 확인해 재사용 가능한 방식으로 보완한다. 공용 Modal 변경이 필요하면 기존 사용 화면도 Reviewer/QA 범위에 넣는다.

## 3. API 호출 계획

계약 정본은 `agent-vault/10-Flow/tasks/task-051-feedback-recall-demo.md`의 실제 구현 API/DTO 절이다. 경로는 단수 `/api/feedback`을 사용한다. 응답은 프로젝트 표준 `{success,data,message}`로 통일한다. 별도의 `/jobs/:jobId` 경로는 만들지 않고 동일 피드백 GET의 `ai` 상태로 polling한다.

| 경로 | 메서드 | 입력 | 화면이 사용할 응답·동작 | 실패 처리 |
|---|---|---|---|---|
| `/api/feedback` | GET | `from,to,page,limit` | `{items,total,page,limit}` | 조회 실패와 빈 목록 구분 |
| `/api/feedback` | POST | `{date,situation,technique,original,clipIds}` | 신규 독립 피드백 DTO | 원문 유지, 생성 결과 ID를 확보한 뒤 후속 작업 |
| `/api/feedback/:id` | GET | ID | 현재 DTO와 `ai` 상태, 완료 후 질문/요약 | 닫기·네트워크 단절 뒤 동일 ID로 복구 |
| `/api/feedback/:id` | PATCH | `{revision,date?,situation?,technique?,original?,clipIds?,cursor?,draftAnswer?}` | 새 revision의 DTO | 409 충돌 시 새로고침 안내, 임의 덮어쓰기 금지 |
| `/api/feedback/:id/answer` | POST | `{revision,turnId,answer,skip?}` | 답변만 저장한 DTO | 저장한 답변을 보존하고 질문 생성만 재시도 |
| `/api/feedback/:id/ask` | POST | `{revision,more?}` | pending DTO. 이후 GET polling | 이미 미답변 질문이 있으면 재사용 |
| `/api/feedback/:id/summarize` | POST | `{revision}` | pending DTO. 활성 답변을 통합한 요약은 GET polling | 기존 원문·답변·요약 보존, 실패 후 재시도 |
| `/api/feedback/:id/results` | POST | `{revision,date,outcome,context,note}` | 연습 결과가 추가된 DTO | 실제 결과 저장과 숙련도는 구분 |
| `/api/feedback/:id/task` | POST | `{revision,expectedTaskId,replace}` | `{feedback,task:{id,nodeId,projectId},reused}` | 현재 과제 CAS/명시 교체와 이력 보존 |
| `/api/feedback/recap` | GET | `from,to` | 기간 내 피드백·실패·연습 결과와 요약 | 적용 기간 일치 확인 |
| 기존 클립 목록/캐시 | GET | 기존 계약 | 상세 객체와 사용 횟수 | 조회 실패 시 선택을 지우지 않음 |
| 기존 `/holes`, `/recall/stale`, `/recall/search` | GET | 기존 옵션과 `from,to` | 선택 기간을 반영한 기존 복기 데이터 | 기간 없는 기존 호출의 의미 유지 |

`/recap`은 `/:id`보다 먼저 마운트한다. 날짜는 실제 날짜 검증과 양끝 포함 조건을 사용한다. 연습 결과 `outcome`은 `not_tried | tried_failed | done`, `context`는 `drill | position_spar | spar | other`다.

확정 DTO는 다음 필드로 프론트와 백엔드를 맞춘다.

```text
{id,date,situation,technique,original,clipIds,clips,turns,archives,cursor,ready,
 summary,summaryStale,summarySourceHash,taskBinding,revision,
 ai:{status:'idle'|'pending'|'failed',kind,error,startedAt},results}
```

질문 `ask`와 답변 `answer`를 분리한다. 답변 저장의 새 revision을 받은 뒤 `ask`를 호출한다. GET polling으로 `ai.status`가 idle/failed가 될 때까지 같은 기록을 조회하고, 패널을 닫아도 원문이나 답변을 재제출하지 않는다. 서버는 오래 걸리는 CLI 실행 중 DB 트랜잭션/락을 유지하지 않는다. pending과 generation token을 먼저 저장하고, 결과 적용 시 revision/token compare-and-set을 수행한다.

## 4. 저장 정본·프론트 상태

확정 저장 방식은 독립 Feedback 모델 1행에 날짜/상황/기술명/원문/clip ID와 JSON 대화·연습 결과·요약을 저장하는 것이다. JSON은 TEXT 저장과 공용 safeParse/DTO 직렬화를 일관되게 사용한다.

- 활성 turn은 `{id,question,answer:null|string,draftAnswer:string,skipped:boolean}`이다.
- `turns`, `archives`, `cursor`, `ready`를 피드백별로 보존한다. 활성 경로 변경과 이력 보관은 원자적으로 처리한다.
- PATCH의 `cursor/draftAnswer`로 이전 이동과 미제출 답변을 저장·재개한다. 같은 답변 제출은 기존 다음 turn을 재사용한다.
- 원문·상황·기술 변경은 기존 대화를 이력으로 보존하고 새 질문 맥락을 시작한다.
- 요약에는 원문/상황/기술/날짜/현재 제출 답변/선택 영상/연습 결과의 입력 snapshot hash를 저장한다. archives와 미제출 draft는 AI 근거에서 제외한다.
- 저장의 optimistic `revision`과 요약 입력 hash를 구분한다. 탐색 cursor 변경만으로 요약 내용을 오래된 것으로 간주하지 않는다. 내용 hash가 달라지면 `summaryStale`을 표시하고 기존 요약은 보존한다.
- 모든 조회/쓰기/영상 연결은 요청 사용자 소유자로 제한한다. `class_id`, `spar_day_id`, 선택 수업 날짜를 피드백 저장의 필수 값이나 자동 기본값으로 사용하지 않는다.

프론트는 DTO를 정본으로 사용한다. FeedbackPanel의 편집 draft, 진행 중 로컬 답변, 조회/polling 상태, 호출 화면 `returnSurface`만 별도 UI 상태로 둔다. 영상 Picker의 검색/필터/기술/페이지/펼침 상태는 선택 영상 ID와 분리하고 기존 CacheContext를 활용한다.

생성/수정/정리 완료 뒤 홈 최근 피드백과 복기 선택 범위의 목록·요약을 무효화한다. 기존 훈련 기록 캐시는 실제 그 기록이 바뀐 경우에만 갱신한다.

### 기존 controller의 데이터 보존·오류 UI 연결

사용할 상태관리 정본은 이미 비화면 검증한 `feedbackRecordController`/`useFeedbackRecord`다. 37/37은 상태기계·순수 함수 근거이며 React/DOM 검증을 대신하지 않는다. 아래 UI는 기존 패널의 오류 영역과 확인 모달 안에서 연결한다. v5의 입력→보완→카드 구조와 기본 CTA를 변경하거나 별도 복구 화면을 만들지 않는다.

| 상태 | 기존 패널 안의 표시·선택 | 보존/호출 원칙 |
|---|---|---|
| 미저장 상태에서 닫기·다른 기록/새 기록 이동 | `저장 후 이동`, `로컬 변경 폐기`, `계속 편집` | saveAndClose/saveAndOpen 성공 후에만 이동. 명시적 폐기만 discardAndClose/discardAndOpen. 기본 이동은 차단 |
| 입력 필드 충돌 `inputConflicts` | 충돌 필드마다 내 값과 서버 값을 함께 표시하고 `내 값 사용`/`서버 값 사용` 선택 | untouched 원격 필드는 병합. 충돌난 동일 필드를 자동 덮어쓰지 않으며 모든 충돌을 명시 해결하기 전 저장/AI 요청 차단 |
| 답변 충돌 `answerConflicts` | 질문 원문과 질문 ID를 확인할 수 있게 표시하고 내 제출/초안과 서버 제출/초안을 비교 | turn별 명시 local/server 선택. 다른 질문의 답변으로 바꾸지 않음 |
| 제거된 질문의 초안 `orphanDrafts` | 보관된 질문·내 초안을 표시하고 `활성 질문에 복구`/`이 초안 폐기` 선택 | 복구 대상은 현재 유효 질문에서 사용자가 고름. 복구는 미제출 초안이며 AI 근거로 자동 승격하지 않음. 대상에 초안이 있으면 자동 덮어쓰지 않음 |
| 신규 생성 응답 유실 `uncertainWrite` | 서버 저장 여부 불명 안내, 내 로컬 입력 유지, `내 피드백 목록 확인`과 사용자 명시 기록 선택 | 날짜 제한 없는 소유 기록 목록으로 확인. 텍스트가 같다는 이유만으로 자동 매칭하거나 create 자동 재시도하지 않음 |
| 저장/답변 제출 대기 중 추가 편집 | 최신 입력이 남아 있다는 안내와 `최신 내용 저장`/답변 제출 선택 | 저장 완료 뒤 현재 편집이 달라졌으면 AI 후속 질문/요약을 자동 진행하지 않음. 자동 반복 저장 금지 |

오류 영역의 `로컬 변경 폐기`는 서버 기록 삭제가 아니다. 복구 대상을 확정하지 못한 생성 응답 유실, 남아 있는 충돌/제거된 질문 초안은 조용히 닫거나 다른 기록으로 전환하지 않는다. 사용자가 폐기를 선택하면 잃게 되는 **로컬** 입력 범위를 확인시키고 명시적 controller 동작을 호출한다. 과거 서버 기록은 그대로 둔다.

현재 질문의 작성 중 답변뿐 아니라 활성 경로에 남은 모든 dirty 답변을 보존한다. 이전 답변을 바꾸기 전 dirty 초안을 저장하고 cursor를 복원하는 controller 순서를 우회하지 않는다. 저장한 초안은 `아직 제출하지 않은 답변`으로 표시하며 sourceQuotes/요약/과제의 활성 근거에 넣지 않는다.

로컬 dirty·충돌·orphan·unknown write·미제출 저장 초안, summary 없음/오래됨, AI pending 상태에서 과제 지정을 허용하지 않는다. 사유와 현재 가능한 저장/복구/재정리 동작을 같은 오류 영역에 보여준다. sourceQuotes는 기존 카드의 교정점 근거 영역에서 원문/활성 답변 출처와 함께 펼쳐볼 수 있게 하고, practiceMethods는 기존 연습 영역에 `연습 제안`으로 표시한다. 실제 시청·과거 성공·확정 기전으로 오표시하지 않는다.

## 5. 실제 관장 CLI의 통합 질문·정리

모든 호출은 기존 `services/claudeCli.js`의 `runClaude`와 `loadPersona`의 gym-master 역할, `masterChat.resolveModel`의 사용자 모델 선택을 재사용한다. 외부 도구는 빈 문자열 인자로 비활성화하고 제공한 데이터만 구조화한다. 관장 역할의 기록 우선·미확인 내용 확인·기술 오매칭 방지·승인 후 과제 생성 원칙을 재사용한다. 현재 관장실의 최근 12개 메시지 창만을 새로운 피드백의 저장 정본으로 사용하면 전체 활성 답변이 누락되므로 별도 피드백 문맥을 조립한다.

### 모델에 전달할 현재 근거

- 피드백 원문과 자유 상황, 선택 기술 또는 기술 미정.
- **현재 활성 경로**의 질문과 답변 전체, 확인 대기 표시.
- 사용자 소유 확인을 마친 선택 영상의 ID·기술명·제목·포지션·설명 등 실제 저장 메타.
- 직접 조회한 관련 훈련 근거가 있으면 날짜/출처 ID와 현재 선택 기간 여부.

보관 경로의 옛 답변은 활성 근거에서 제외한다. 영상 제목/설명만 받은 경우 영상을 실제로 시청했다거나 특정 타임코드를 확인했다고 쓰지 않는다.

### 질문 결과 계약

한 호출은 다음에 필요한 질문 하나 또는 정리 제안을 반환한다. 질문 횟수에 고정 상한을 두지 않는다. 이미 확인된 사실은 다시 묻지 않고, 모르는 내용은 확인 대기로 남기며 가능한 확인 방법을 제안한다. 사용자 요청으로 언제든 통합 요약할 수 있다.

질문 응답은 `{question:string|null,ready:boolean,reason:string}` 스키마를 검사한다. `question`이 있으면 활성 turn으로 저장하고, `ready=true`이면 정리 제안을 표시한다. 기존 관장실의 평문 응답 계약을 전역 변경하지 않는다.

### 통합 요약 결과 계약

확정 통합 요약 스키마는 다음과 같다.

```text
{title,overview,
 correctionPoints:[{title,detail,evidenceTurnIds:[],
   sourceQuotes:[{source:'original'|'turn',turnId:null|id,quote}]}],
 practiceMethods:[{title,steps:[],check,proposal:true}],
 unresolved:[]}
```

`correctionPoints`의 본문에 원문과 활성 보완 답변을 함께 반영한다. 확인된 사실로 서술할 수 있는 내용은 사용자가 명시적으로 입력한 범위다. 원문에 없는 인과 기전, 반복 실패·과거 성과, 사용자의 기억·심리 상태를 관장이 사실로 보충하지 않는다. 필요한 비명시 내용은 `unresolved`의 추가 확인 질문으로 남긴다.

교정점의 `sourceQuotes`는 현재 원문 또는 제출이 확정된 현재 활성 답변의 정확한 인용이다. 서버는 다음 조건을 검사한다.

- `source:'original'`은 `turnId:null`이며 `quote`가 현재 `original`의 비어 있지 않은 정확한 부분 문자열이어야 한다.
- `source:'turn'`은 `turnId`가 제출 완료된 활성 turn의 ID이고 `quote`가 그 turn의 현재 `answer`에서 비어 있지 않은 정확한 부분 문자열이어야 한다. 보관 경로·미제출 draft·이전 수정 답변은 허용하지 않는다.
- `evidenceTurnIds`는 현재 제출된 활성 답변 ID 집합에 속해야 하며, 각 교정점의 turn 인용이 참조하는 ID 집합과 일치해야 한다. 원문 인용만 있으면 빈 집합을 사용한다.
- quote를 모델이나 서버가 문장 교정·의역해 exact 인용처럼 저장하지 않는다. 불일치 결과를 성공 요약으로 승격하지 않고 기존 내용과 오류/재시도 상태를 보존한다.

유효한 인용과 ID 집합은 출처의 존재를 검증하지만, 교정점 전체의 의미 충실성이나 인용에서 추가한 인과 추론까지 보장하지 않는다. 예를 들어 실제 입력 한 문장을 인용해도 입력에 없는 반복 실패나 기전을 detail에 덧붙일 수 있다. 구조 검증과 함께 아래 실제 CLI 재검증이 필요하다.

`practiceMethods`는 과거의 수행 사실과 분리된 미래의 연습 제안이다. 각 항목에 `proposal:true`를 요구하고 기존 카드의 연습 섹션 제목/설명에서 `연습 제안`임을 명시한다. 기존 정리 카드의 배치·흐름·CTA는 유지하며 새 정보구조나 화면을 추가하지 않는다. 단계와 적용 확인 기준은 `steps/check`로 렌더하고 이미 연습했거나 성공한 것처럼 표현하지 않는다. 확인되지 않은 사실과 확인 방법은 `unresolved`에 남긴다. 연결 영상 목록은 DTO의 사용자 소유 `clips`를 사용하며 모델이 임의 영상을 만들지 않는다.

원문과 활성 답변이 충돌하면 임의로 하나를 사실로 확정하지 않고 확인 대상으로 표시한다. 프론트는 저장된 구조를 렌더하고 보우 예시나 규칙 문장을 정적 결과로 사용하지 않는다.

입력 snapshot hash가 달라지면 서버 DTO의 `summaryStale`로 기존 카드를 `이전 내용 기준`으로 표시하고 다시 정리를 요청할 수 있게 한다. 늦게 도착한 옛 revision/generation token의 결과는 CAS로 현재 카드에 적용하지 않는다.

### 예산·실패·재시도

- 대화 질문 수와 한 CLI 실행의 도구 턴 제한은 구분한다. 기존 `MAX_TURNS`를 대화 전체의 질문 수 상한으로 해석하지 않는다.
- 입력 길이·바이트·실행 시간 예산을 확인한다. 전체 활성 문맥을 보낼 수 없으면 누락·잘림을 숨기거나 완료로 처리하지 않고 입력 예산 오류를 표시한다. 원문과 답변은 보존한다.
- pending·네트워크 단절·서버 재시작·CLI 실패·출력 형식 오류를 구분할 수 있는 상태를 저장한다. 기존 큐/재시도 원칙을 재사용하며 동일 요청 재시도로 답변/요약이 중복 생성되지 않게 한다.
- 모델이 반환한 근거 ID·clip ID는 현재 기록의 허용 집합과 대조한다. 없는 근거·타인 영상·임의 URL을 카드에 연결하지 않는다.
- 계정당 열린 과제 하나 규칙을 유지한다. 피드백 정리만으로 숙련도나 훈련 성공을 올리지 않는다. 과제 CTA의 v5 의미를 보존하는 확정 계약은 다음 절과 같다.

### v5 과제 CTA의 확정 구현

**피드백의 과제 설정 엔드포인트에서 기존 연구 write 서비스를 호출한다.** v5는 `이번 주 과제로 정하기`를 누르면 지정하고, 열린 과제가 있으면 `기존 과제 유지 / 이 과제로 바꾸기`를 선택하는 직접 승인 흐름이다. 이 정보구조와 버튼의 의미를 유지해야 한다.

기존 연구 과제는 `nodeId`가 필수다. Leader가 승인하고 Backend가 구현한 과제 설정 계약은 다음과 같다.

```text
POST /api/feedback/:id/task
{revision,expectedTaskId:null|positive,replace:boolean}
→ {feedback,task:{id,nodeId,projectId},reused}
```

카드에는 실제 과제로 사용할 첫 교정점/연습의 제목과 요지를 버튼 위에 표시한다. 첫 항목을 과제 node의 note로 요약하되 전체 근거의 연결은 feedback ID로 유지한다. 전체 새 관장 대화를 띄우는 추가 단계는 두지 않는다.

1. 사용자 소유 피드백과 현재 통합 요약을 확인하고 카드에 제안한 교정점/연습 하나를 과제 대상으로 사용한다. summaryStale 또는 AI pending이면 설정을 거부하고 갱신/진행 상태를 안내한다.
2. 사용자가 버튼을 눌러 승인한 뒤 단일 트랜잭션 안에서 기존 researchWrite helper로 연구 project·node·과제를 생성한다. feedback의 taskBinding은 같은 summary snapshot의 기존 결과를 재사용한다. 재사용할 과제가 실제 현재 열린 과제인지 확인하여 마감/교체된 과제를 현재 설정됨으로 표시하지 않는다.
3. expectedTaskId로 현재 열린 과제를 CAS 확인한다. 일치하지 않거나 교체 승인이 없으면 409를 반환하고 현재 과제를 갱신한 뒤 v5의 기존 유지/바꾸기 UI를 보여준다. 명시적 바꾸기 승인 후에만 실제 setWeeklyTask의 not_tried 이력 마감 규칙을 보존하여 원자적으로 교체한다.
4. 실패하면 중간 project/node만 남기지 않고 롤백한다. 선택한 피드백과 요약의 revision/내용을 대조하여 다른 내용으로 과제를 만들지 않는다.

대안 `useMaster.startChat(seed)`는 통합 요약의 교정점/대표 연습 하나를 2,000자 이내로 전달해 실제 관장실의 제안→승인 흐름을 재사용할 수 있다. 다만 v5의 직접 지정/교체에서 별도 관장 대화와 추가 승인 단계로 사용자 행동이 바뀌므로 **동일 의미의 구현 차이로 처리하면 안 된다.** 이 대안을 선택하려면 Leader가 material 차이로 판단하고 해당 흐름의 데모 재검토를 진행해야 한다.

## 6. 기간별 복기

기존 RecallPage의 실패 집계·미연결 기술·잊기 직전·포지션 격자·검색을 임의로 제거하지 않는다. 상단 기간 선택을 공통 기준으로 삼고 새 피드백 영역을 추가한다.

- 월은 당월 1일~말일, 주는 월~일, 직접선택은 양끝을 포함한 YYYY-MM-DD 문자열 범위다. 전체는 날짜 제한을 생략한다.
- 사용자 입력 날짜를 UTC 변환해 하루를 이동시키지 않는다. 현재 KST 기준 날짜 헬퍼를 재사용한다.
- 피드백은 피드백 날짜, 스파링 근거는 실제 스파링 날짜, 연습 결과는 실제 적용 날짜로 제한한다. 수업 시작일만으로 다른 날 스파링을 잘못 포함하지 않는다.
- 실패/성공/원인 집계·연습 근거·포지션 격자도 해당 범위의 코퍼스를 사용한다. 전체기간 데이터를 받는 기존 `/api/holes` 호출에 UI 필터만 추가해 기간 요약이라고 표시하지 않는다.
- 잊기 직전·숙련도처럼 누적 상태가 필요한 정보는 누적 기준임을 표시하고, 선택 기간 내 활동 근거와 구분한다. 기간 안 실패 횟수와 기술 숙련도의 누적 증거를 혼동하지 않는다.
- 기간 밖 과거 근거를 관장이 참고하면 날짜와 `기간 밖 참고`를 표시하고 선택 기간 집계에는 넣지 않는다.
- 역전된 직접선택 날짜는 적용하지 않고 오류와 현재 적용 중인 유효 범위를 함께 표시한다. 빈 결과와 조회 실패를 구분한다.

## 8. 구현·검증 순서

1. 최신 사용자 명시 지시와 Leader의 frontend 전체 GO에 따라 승인 v5 및 이 최종 가이드로 실제 화면 구현을 계속한다. 기록 도구 문제 때문에 동일 승인을 재요청하지 않는다.
2. Backend와 프론트는 task의 Feedback 단일행·revision/CAS·ask/GET polling·기간 계약과 같은 DTO로 연결한다.
3. 입력·저장·조회·재개와 실제 CLI 질문/통합 요약을 먼저 끝까지 연결한다.
4. 기존 클립 필터·5개 페이징·공용 팝업과 홈/수업 헤더 진입을 연결한다.
5. 기존 복기 집계의 실제 날짜 제한과 새 피드백을 같은 기간으로 검증한다.
6. Reviewer 독립 검토 후 QA가 아래 회귀를 검증한다. 배포는 별도 절차를 따른다.

필수 회귀는 독립 빈 입력, 다른 수업 선택 후에도 오늘 날짜, 기술 미정, 일반 기록과 보우 기록 격리, 실제 CLI의 답변 반영, 5+2/정확5/빈 영상 결과, 필터 후 숨은 선택 유지, 공용 팝업 포커스·스크롤 복귀, 질문 수 가변/이전 미제출 답변/동일 답변 경로 유지/변경 경로 이력, 오래된 요약과 늦은 결과, 동시 수정·중복 재시도, 기간 양끝·월/주/윤년 경계, 360/390/412px다.

요약 계약의 sourceQuotes/proposal 보완은 실제 CLI QA에서 활성 정정은 반영했으나 입력에 없는 인과 기전·반복 실패·기억 상태를 사실로 단정한 HIGH 결함을 해결하기 위한 것이다. Backend 수정 이후 실제 CLI를 재실행하여 원문·활성 정정의 통합, exact 인용과 ID 집합, 미명시 기전/성과/심리 단정의 부재, 연습의 미래 제안 표시, 미확인 내용의 추가 질문 처리를 다시 검증한다. 인용/스키마 단위 검사만으로 이 결함의 해결을 주장하지 않는다. 이 가이드의 변경만으로 실제 CLI 재검증이 완료된 것은 아니다.

데모 브라우저 검증, 고립된 자동 검사, 실제 CLI 실행, 실제 로그인/API·DB 저장, 배포 검증은 각각 증거를 구분한다. 실제 CLI 검증이 생략되거나 실패하면 `incomplete`와 원인·미검증 범위를 기록한다.
