## 1. 목적과 범위

수업(배움) → 스파링(시험) → **복기(진단)** → **연구(과제)** → 다음 스파링 루프를 돌리기 위한 사양이다.

이 기능군의 급소는 전부 한 곳에 몰려 있다. **"스파링에 적은 기술명"과 "기술트리(`techniques.name`)"가 문자열로 만나는 지점**이다.
구멍 목록·사다리 4·5단계·리액션 자동 유입이 모두 이 조인 위에 얹힌다.
표기가 갈리면 에러가 나지 않고 **조용히 0건**이 된다 — 이 프로젝트가 이미 두 번 당한 실패 방식이다
(task-014 NFD split-brain, task-016 "성공 응답인데 7행 잔존").

그래서 이 문서는 설계보다 **실측을 먼저** 싣는다. §2의 수치가 §5·§7의 근거다.

## 2. 실측 결과 — 이름이 만나는 지점

측정 대상은 실사용자 `user_id=3`. admin(`user_id=1`)은 분리해 제외했다.

| 저장소 | user_id=3 | user_id=1 | 비고 |
|---|---:|---:|---|
| `techniques` | 47 | 1 | 관례상 알려진 "47건"이 맞다. 전체 48은 admin 1건 포함 |
| `spar_sessions` | 54 | 0 | 소유는 `spar_days.class_id → classes.user_id` 경유 |
| `drills` | 29 | 0 | 동일하게 `classes` 경유 |
| `video_clips` | 134 | 0 | `user_id` 직접 보유 |
| `classes` | 29 | 3 | |

> ⚠️ `spar_sessions`·`spar_days`·`drills`에는 **`user_id` 컬럼이 없다.** 소유자 판별은 반드시
> `classes`까지 조인해야 한다. 이 조인을 빠뜨리면 사용자 간 데이터가 섞인다.

### 2.1 기술명 매칭률 (★ 핵심 수치)

`spar_sessions.success`의 기술명 → `techniques.name`(user 3, 47건) 매칭.
NFC 정규화 후 3단 비교. 정규화 유틸은 신규 작성하지 않고 기존 것을 재사용했다(§7).

모집단: success가 채워진 라운드 **38/54**, 기술명 등장 **83건**, 고유 **48종** (성공 45 · 실패 38)

| 단계 | 판정 | 고유 종수 | 등장 건수 |
|---|---|---:|---:|
| (a) 완전 일치 | NFC 정규화 후 문자 그대로 같음 | 14종 (29.2%) | 38건 (45.8%) |
| (b) 정리 후 일치 | 공백·괄호·대소문자·중점 제거 + 별칭 사전 + fuzzy | 3종 (6.3%) | 4건 (4.8%) |
| **(c) 미매칭** | **어느 쪽으로도 안 맞음** | **31종 (64.6%)** | **41건 (49.4%)** |

> 🔴 **스파링에 적힌 기술명의 절반(49.4%)이 기술트리에 닿지 못한다.**
> 지금 이 상태로 구멍 목록·사다리를 붙이면 절반이 조용히 사라진다.

미매칭 31종(승인 대상)은 원인이 4가지로 갈린다. 성격이 다르므로 처리도 달라야 한다.

| 유형 | 예시 | 처리 방향 |
|---|---|---|
| **A. 포지션+기술 복합어** (가장 많음) | `마운트 암바` · `오픈가드 암바` · `스카프홀드 암바` · `숄더 암바` · `리버스 기무라` · `오픈가드 패스` · `오픈가드 스윕` · `델라리바 스윕` · `라쏘 스윕` · `싱글엑스 스윕` | 트리는 기술명만(`암바`), 스파링은 포지션을 붙여 적는다. **§6 노드 모델(포지션·피니시 분리)은 앞으로 쌓일 기록에 대한 해법이지, 이미 `spar_sessions.success`에 문자열로 적힌 `마운트 암바`를 `암바`에 붙여주지는 않는다**(자카드 0.5로 여전히 미매칭). 이름을 억지로 맞추지는 말되, **이미 적힌 문자열의 매칭 문제는 별도 과제로 남는다**(§6 설계 메모 참고) |
| **B. 별칭 사전 누락** | `삼각 쵸크`(→트라이앵글 쵸크) · `보우앤애로우 쵸크` · `암락` · `백 쵸크` · `다스 쵸크` · `닌자 쵸크` | `utils/techAliases.js`에 항목 추가로 해결 |
| **C. 트리에 없는 기술** | `엑스패스`(드릴에도 등장) · `크레이지독 패스`(4회) · `니컷` · `밸리다운` · `100퍼스윕` · `윌리엄 가드` | 사용자에게 "트리에 추가할까요?" 제안. **자동 생성 금지**(기존 설계 원칙 유지) |
| **D. 오타** | `싱글렏 스윕`(← 싱글렉) | 사용자 확인 후 수정 |

🔴 **B 유형에서 발견된 실제 모순 1건** — 같은 기술을 두 가지로 적었는데 한쪽만 매칭된다.

| 스파링 표기 | 결과 | 이유 |
|---|---|---|
| `보우 앤 애로우 쵸크` | ✅ fuzzy 매칭 → `보우 앤 애로우` | 토큰 {보우,앤,애로우,쵸크} ∩ {보우,앤,애로우} → 자카드 0.75 |
| `보우앤애로우 쵸크` | ❌ 미매칭 | 토큰 {보우앤애로우,쵸크} ∩ {보우,앤,애로우} → 자카드 **0** |

`techMatch.js`의 fuzzy 단계가 쓰는 `tokenize()`는 **공백으로만 단어를 나눈다.** 반면 2단계 `normalize()`는
공백을 아예 제거한다. 그래서 띄어쓰기만 다른 같은 이름이 exact에서는 흡수되지만 fuzzy에서는 **전혀 다른 이름**이 된다.
띄어쓰기가 매칭 성패를 가르는 이 비대칭은 사용자에게 설명 불가능한 동작이다.

`테크니컬 스탠드업 (Technical Standup)` · `무릎 압박 패스 방어 (Knee Press Pass Defense)` · `펜듈럼 스윕` ·

여기서 **`(영문)` 병기 표기**가 별도 계열로 발견된다(`키마라 (Kimura)` 등). 괄호를 벗겨도
`키마라`≠`기무라`, `시저 스윕`≠`시저스 스윕`이라 여전히 안 맞는다. 괄호 제거만으로는 부족하다.

또 **`엑스패스`는 드릴과 스파링 양쪽에 등장하는데 트리에만 없다** — 오타가 아니라 진짜 누락이다(C 유형).

### 2.3 포지션 어휘 현황 (4개 저장소 전수)

고유 포지션명은 **세는 기준에 따라 갈린다.** 4개 저장소(`user_id=3`) 전수 기준:

| 기준 | techniques | drills | video_clips | spar_sessions | 합집합 |
|---|---:|---:|---:|---:|---:|
| **원본 문자열 기준** | 6 | 10 | 9 | 12 | **25종** |
| **정규화키 기준** (`normalize()` 적용) | 6 | 10 | 9 | 12 | **24종** |

이 문서에서 말하는 **"고유 포지션명 25종"은 원본 문자열 기준**이다. 정규화키 기준으로는 24종이다.
두 값이 갈리는 원인은 **단 한 쌍뿐** — `오픈가드` / `오픈 가드` (띄어쓰기만 달라 정규화키가 같다).
이는 아래 Tier A의 **A-1 병합 제안과 정확히 같은 항목**이다.

> 이 4개 저장소의 포지션 값에 **NFD 잔존은 0건**이다(원본 바이트 기준 25종 = NFC 정규화 후 25종).
> §7.2의 "NFD 잔존 0건"이 포지션 컬럼에도 성립함을 확인했다.

저장 형식은 저장소마다 다르다.

| 저장소 | 컬럼 | 형식 | 종수(원본 문자열 기준) |
|---|---|---|---:|
| `techniques` | `pos` (text) | JSON 배열 `["가드 (Guard)"]` | 6 |
| `drills` | `pos` (**varchar(50)**) | **단일 문자열** (배열 아님) | 10 |
| `video_clips` | `position` (text) | JSON 배열 | 9 |
| `spar_sessions` | `positions` (longtext, `json_valid` CHECK) | JSON **객체** 배열 `[{name,score}]` | 12 |

**정규화키 기준 저장소 간 교집합** (행∩열 / 행 전체):

| | techniques | drills | video_clips | spar_sessions |
|---|---|---|---|---|
| **techniques** | (6) | 2/6 | 5/6 | 2/6 |
| **drills** | 2/9 | (9) | 5/9 | 1/9 |
| **video_clips** | 5/9 | 5/9 | (9) | 3/9 |
| **spar_sessions** | 2/12 | 1/12 | 3/12 | (12) |

> ⚠️ **각주 — 매트릭스의 `drills` 분모 9는 위 표의 drills 종수 10과 어긋난다.**
> 위 표는 원본 문자열·정규화키 **어느 기준으로도 drills를 10종**으로 센다. 매트릭스의 9가 무엇을 세어
> 나온 값인지 근거가 남아 있지 않아 **추측으로 고치지 않고 그대로 둔다.** 따라서 매트릭스는 저장소 간
> 겹침의 **경향**을 읽는 용도로만 쓰고, 정확한 종수는 반드시 위 표를 근거로 삼을 것.
> (`techniques` 6 · `video_clips` 9 · `spar_sessions` 12는 위 표와 일치한다. 어긋나는 것은 drills 한 행뿐이다.)

> 🔴 **스파링 포지션 어휘는 사실상 고립돼 있다.** 12종 중 다른 저장소에 존재하는 것은 3종뿐
> (`오픈가드` · `사이드 컨트롤` · `탑 포지션`). 나머지 9종(`탑` · `사이드 포지션` · `탑 컨트롤` ·
> `남북 포지션` · `백 포지션` · `델라리바` · `헤드쿼터` · `스카프홀드` · `클로즈가드`)은 **어디에도 없다.**

**어휘 계열이 실제로 다르다** — 지시서가 짚으라고 한 지점이 사실로 확인됐다.

- **드릴 어휘**: 가드 · 백 · 스탠딩 · 터틀 · 패스 · 하프가드 탑 · 오픈가드 탑 — *동작·국면* 중심
- **기술트리 어휘**: 가드 · 탑 포지션 · 마운트 · 사이드 컨트롤 · 백 · 기타 — *대분류 6칸* (`기타` 존재)
- **스파링 어휘**: 오픈가드 · 클로즈가드 · 탑 · 탑 컨트롤 · 사이드 포지션 · 남북 포지션 · 헤드쿼터 · 델라리바 · 스카프홀드 — *실전에서 실제로 거친 자리*, 훨씬 세분화

기술트리는 6칸짜리 서랍이고 스파링은 12칸짜리 실황이다. **한쪽으로 억지 통합하면 정보가 소실된다.**

## 3. 스키마 변경 (DDL)

task-022의 DDL과 동일하다. **사전 충돌 확인 완료(2026-09-06 실측)**:
`spar_causes` 테이블 없음 / `spar_sessions`에 `cause_ids`·`reaction` 컬럼 없음 → 충돌 없음.

환경: **MariaDB 10.11.11**, `sql_mode = STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`

```sql
CREATE TABLE spar_causes (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  name VARCHAR(40) NOT NULL,
  sort INT DEFAULT 0,
  active TINYINT DEFAULT 1,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
-- 초기 4개 시드(user_id별): 그립 · 각도 · 타이밍 · 연결 없음

ALTER TABLE spar_sessions ADD COLUMN cause_ids TEXT DEFAULT '[]';   -- 실패 항목별 태그 id
ALTER TABLE spar_sessions ADD COLUMN reaction  TEXT DEFAULT '[]';   -- 실패 항목별 막힌 리액션 한 줄
```

적용 시 준수 사항:

- MariaDB 10.2+는 TEXT에 `DEFAULT`를 허용하므로 위 DDL은 그대로 통과한다.
- **STRICT 모드이므로 길이 초과는 에러다.** `name VARCHAR(40)` 상한을 프론트·백엔드 양쪽에서 막을 것.
- 적용 전 `information_schema`로 존재 확인 후 실행(기존 데이터 보호).
- **`outcome` 컬럼과 기존 값은 유지한다. DROP 금지.** 화면에서만 제거한다.

### 3.2 `recall_summaries` — AI 복기 카드 캐시 (task-025, 적용 완료)

착수 전 `information_schema` 확인: `%recall%`·`%summar%`·`%cache%` 전부 0건 → 충돌 없음.
추가만 하는 DDL 이라 기존 데이터 위험은 0 이다(ALTER 없음, 신규 테이블 1개).

```sql
CREATE TABLE recall_summaries (
  id             INT AUTO_INCREMENT PRIMARY KEY,
  user_id        INT NOT NULL,
  query_norm     VARCHAR(200) NOT NULL,   -- 검색 조건 전체(q + pos + from + to)
  class_ids_hash CHAR(64) NOT NULL,       -- sha256(정렬된 classId 목록)
  content        MEDIUMTEXT,
  prompt_chars   INT DEFAULT NULL,        -- QA 관측용
  created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_recall (user_id, query_norm, class_ids_hash),
  INDEX idx_rs_user (user_id)
);
```

- `UNIQUE` 3열이 캐시 키다. `query_norm` 에 `pos`/`from`/`to` 가 들어가야 한다 —
  `q` 만 쓰면 조건이 다른 검색이 같은 요약을 받는다.
- `class_ids_hash` 가 **자동 무효화** 장치다. 수업이 추가되면 해시가 달라져 새로 만든다.
- 🔴 `query_norm` 은 STRICT 모드의 `VARCHAR(200)` 이라 201자는 잘림이 아니라 **에러**다.
  `buildQueryNorm()` 이 200자를 넘을 수 없게 만든다(초과 시 sha256 표기 65자로 대체).
- 이 DB 는 전 테이블 **utf8mb3** 라 4바이트 문자(이모지)는 `Incorrect string value` 500 이 된다.
  라우트에서 400 으로 먼저 거른다(task-022 `spar_causes` 와 같은 처리).

  가진 이름이 둘 이상이면 합치지 않고 `summary.sameTechnique` 로 **드러낸다**.
- **미연결(`unlinked`)은 threshold 와 무관하게 전부 반환**한다. 미매칭 이름은 대개 실패 1건이라
  threshold 에 걸려 `holes` 에서 빠지는데, 화면에서는 "매칭이 안 돼서"와 "횟수가 낮아서"가 구분되지
  않는다. `linked` 와 `isHole` 을 따로 두어 두 이유를 분리한다.
- **`status` 는 `done`/`not_yet`/`no_record` 3값**이다. 표본이 0건이면 `0/0` 이 아니라 `no_record` —
  "아직 못 했다"와 "잴 기록이 아예 없다"는 다른 말이다.
- **`reached` 는 done 인 단계 중 최댓값**이다. 사다리는 연속이 아니다 — 드릴로 배운 적은 없는데
  스파링에서만 성공한 기술이 실제로 있다(`니슬라이드`: 1단계 ✗, 4·5단계 ✓).
- **벨트 서열 맵은 영문+한글 병기 필수**(§5.3). `belt_history` 에 `white` 와 `화이트` 가 섞여 있어
  한쪽만 매핑하면 5단계가 20건→6건으로 줄고 14건이 에러 없이 사라진다. 매핑에 없는 값은
  `console.warn` + 응답 `unknownBelts` 로 노출한다.
- **"본인 벨트"는 그 스파링 날짜 시점의 벨트**(`achieved_date <= spar_days.date` 인 마지막 행).
  현재 벨트로 전 기간을 판정하면 20건→10건으로, 절반만 어긋나 그럴듯해 보인다.
- 저장소: `technique_mastery` (2·3단계 전용). **행이 없는 것이 정상 상태**이고 시드하지 않는다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/api/recall/search?q&pos&from&to` | 수업기록 통합 검색 — `classes.note`·`theme`·`voice_transcript` + `drills.pos`·`tech` |

구현: `routes/recall.js` · `services/recallSearch.js`(전부 순수 함수) ·
`services/labAnalytics.js`의 `computeStale()` · `models/RecallSummary.js`.

구현하며 확정한 사항:

- 🔴 **텍스트 매칭에 SQL `LIKE` 를 쓰지 않는다.** SQL 은 유니코드 정규화를 못 해서 NFD(자모분리)로
  친 검색어가 **에러 없이 0건**이 된다(task-014 의 실패 방식). 실측으로 확인했다 —
  같은 `가드` 로 `LIKE` 는 NFC 12건 / NFD **0건**, JS 매칭은 25건 / 25건.
  SQL 은 `WHERE c.user_id = ?` 와 날짜 범위만 좁히고 매칭은 JS 에서 `toNFC()` 양쪽 적용 후 한다.
  데이터가 작아(수업 29건 · 전사본 104KB) 전량 메모리 처리로 충분하다.
- 🔴 **전사본 본문을 응답에 싣지 않는다.** 키워드 주변 ±80자 스니펫, 필드당 최대 3윈도우.
  겹치는 윈도우는 병합하되 **윈도우 하나의 길이에 상한(2×radius+검색어)을 둔다** —
  상한이 없으면 키워드가 촘촘한 텍스트에서 병합 윈도우가 계속 자라 전사본을 통째로 싣는다
  (실측: 상한 없을 때 1,287자까지 자랐다. 규칙상 상한은 494자).
  `theme` 만 예외로 통째로 싣는다(varchar(200) 이라 200자를 넘을 수 없다).
- 🔴 **AI 프롬프트 예산 20,000자를 구조적으로 보장한다.** 초과를 예외로 잡는 게 아니라
  블록을 넣기 전에 자리를 확인하고 없으면 안 넣는다. `claudeCli.js` 하드캡은 24,000자인데
  이 계정 전사본 합계는 **104,283자 — 하드캡의 4.3배**다.
  배분은 2단계다: ① 최근순으로 축약 블록 자리를 먼저 확보 → ② 남은 예산으로 최근순 승격.
  한 번에 처리하면 **오래된 수업이 최근 수업보다 상세해지는 우선순위 역전**이 생긴다.
  실측: 검색어 969가지 전수 스윕에서 최대 19,996자, 예산 초과 0건 · 버려진 수업 0건 · 역전 0건.
- 🔴 **`buildRecallPrompt()` 는 순수 함수로 export 한다.** HTTP 만으로는 프롬프트 길이를 잴 수 없어
  QA 가 "코드를 봤더니 넘칠 리 없더라"로 후퇴하게 되기 때문이다(`labAnalytics` 가 벨트맵을
  주입 가능하게 만든 것과 같은 이유). 편의가 아니라 **설계 요건**이다.
- **구멍 기술 제외는 프론트가 아니라 `/api/recall/stale` 이 한다.** QA 가 API 한 번으로 중복 없음을
  판정할 수 있어야 하고, 두 곳에서 걸면 어긋났을 때 원인 추적이 불가능해진다.
  제외한 사실은 `excludedHoleNames` · `excludedTechniqueIds` 로 **드러낸다**.
- **`status` 는 `stale` / `no_record` 2값**, `no_record` 의 `daysSince` 는 0 이 아니라 `null` 이다.
  정렬에서도 섞지 않는다(stale 먼저, no_record 뒤).
- 오늘 날짜는 UTC 에 +9시간을 더해 **명시적으로** KST 를 만든다. `toISOString()` 도, 서버 TZ 설정도
  믿지 않는다(`coachAnalytics` 의 UTC 버그가 후자로 생겼다).
- 캐시 키는 `(user_id, query_norm, class_ids_hash)` 3개다. `query_norm` 에 `pos`/`from`/`to` 를
  **포함해야 한다** — `q` 만 쓰면 조건이 다른 검색이 같은 요약을 받는다.
  `class_ids_hash` 는 요약에 들어간 수업 id 목록의 sha256 이라 **수업이 추가되면 자동 무효화**된다
  (별도 만료 정책이 필요 없는 이유). `UNIQUE` 가 동시 요청 경합을 DB 층에서 막고,
  충돌 시 상대가 넣은 행을 읽어 돌려준다.
- 🔴 `query_norm` 은 `VARCHAR(200)` + STRICT 라 201자는 잘림이 아니라 **에러**다.
  라우트가 검색어를 200자에서 400 으로 막고, 그와 별개로 `buildQueryNorm()` 이 조합 키가
  200자를 넘으면 sha256 표기(65자)로 대체해 **구조적으로** 보장한다.
  이 DB 는 전 테이블 utf8mb3 라 이모지는 `Incorrect string value` 500 이 되므로
  task-022 의 `spar_causes` 와 같은 방식으로 400 으로 거른다.

#### 4.4.1 확정 사항 — 다음 사람이 되돌리기 쉬운 것들

- 🔴 **`sort_order` · `version_no`** — `order` 는 MariaDB 예약어라 `CREATE TABLE t (order INT)` 가
  문법 에러다. 짝을 맞추려고 버전 번호도 `version_no` 로 했다(기존 `chain_steps.step_order` 관례와 일치).
  **DB 컬럼 · Sequelize 속성 · API JSON 필드가 전부 한 이름이다.** "정리"하려고 `order` 로 바꾸지 마라.
- 🔴 **`research_nodes.parent_node_id` 에는 FK 가 없다**(자기참조 CASCADE 는 다루기 어렵다).
  그래서 **노드 삭제 시 앱이 자손을 수집해 지운다** — `researchTree.collectSubtreeIds()`.
  한 단계만 지우면 손자가 고아가 되고, FK CASCADE 는 그걸 못 잡는다. 나머지 FK 4건은 실재한다
  (`fk_rv_project`·`fk_rn_version` CASCADE, `fk_rn_tech` SET NULL, `fk_rl_node` CASCADE — 전부 InnoDB 실측 확인).
- 🔴 **`kind` 와 깊이 사이에 제약이 없다.** `포지션` 도 어느 깊이에나 온다(실제 수업 theme 이
  `"싱글엑스 가드 -> 50대50"` 처럼 중간에 자리를 바꾼다). 루트 전용으로 만들지 마라.
- 🔴 **사다리 상태를 노드에 저장하지 않는다.** 사다리는 기술 단위(`technique_mastery`)다(§5.1).
  `research_nodes` 에 `drilled`/`position_spar` 류 컬럼을 추가하는 순간 같은 기술의 두 노드가
  다른 사다리를 보게 된다.
- **트리 무결성 3검사**(순환 금지 · 같은 버전 · 깊이 상한 12)는 `researchTree.validatePlacement()` 하나가
  담당하고 위반은 400 이다. 🔴 깊이는 **서브트리 전체 높이**로 판정한다 — 옮기는 노드 하나만 보면
  깊은 가지를 상한 너머로 밀어 넣을 수 있다.
- **소유 판별은 `resolveOwned()` 하나**를 거치고, 그 SQL 은 예외 없이 `research_projects` 까지 조인한다.
  하위 3테이블의 `user_id` 는 부모에서 유도해 채우는 **사본**이고 권한 판정에 쓰지 않는다 —
  드리프트를 SQL 로 검출하기 위한 관측 장치다. 없는 것과 남의 것은 **둘 다 404** 다(§4.2 와 같은 규칙).
- **날짜는 `DATE_FORMAT(..., '%Y-%m-%d')`** 로 만든 문자열이다. DB 세션 TZ 가 `SYSTEM`=KST 라
  그대로 KST 날짜가 된다. `toISOString()` 은 쓰지 않는다(UTC 변환으로 하루가 밀린다).

#### 4.4.2 진척 2축 정의 (정본)

```
① 대처 채움률
   분모 = 활성 버전의 kind='리액션' 노드 수      ← 전체 노드 수도, 대처 노드 수도 아니다
   분자 = 그중 직계 자식에 kind='대처'가 하나 이상 있는 노드 수
   리액션 0개 → ratio: null   (화면은 "리액션 없음". 0/0 이 아니다)
   응답에 uncoveredReactionNodeIds[] 를 함께 싣는다 — 프론트가 다시 판정하지 않게

② 사다리 평균
   분모 = 활성 버전 노드들이 참조하는 고유 technique_id 수 (NULL 제외)  ← 노드 수가 아니다
   값   = 각 기술의 GET /api/mastery 의 reached,  평균은 소수 1자리
   고유 기술 0개 → avgReached: null  (화면은 "기록 없음". 0.0/5 가 아니다)
```

🔴 **`loadLabData(userId)` 는 요청당 딱 한 번.** 목록 API 에서 프로젝트마다 부르면 N+1 이다.
전 프로젝트의 고유 기술을 모아 한 번에 `reached` 맵을 만든 뒤 나눠 쓴다.

#### 4.4.3 해석을 정한 지점 — `move` 의 `sortOrder`

계약이 `{parentNodeId, sortOrder}` 까지만 정하고 형제 처리를 정하지 않았다.
**`sortOrder` 를 목적지 형제들 사이의 index 로 해석하고, 이동 후 목적지 형제를 `0..n-1` 로 다시 매긴다.**
INT 사이에 값을 끼워 넣을 수 없어서다 — `0,1,2,3` 에서 "1번 자리로"를 raw 값으로 표현할 방법이 없고,
index 로 두면 한 번의 호출로 순서 변경이 끝난다. 부모가 바뀌면 원래 부모의 형제도 다시 매긴다.
재번호는 **UPDATE 뿐**이다(행을 지우고 다시 넣지 않는다 — §4.4.1 의 PATCH 부분 갱신 원칙과 같은 이유).
🔴 **`insert-parent` 는 형제를 재번호하지 않는다** — 계약 B-1 이 "A·B 의 sort_order 는 변하지 않는다"를
명시했기 때문이다. 두 라우트의 형제 처리가 다른 것은 의도된 것이다.

### 5.2 현 스키마로 계산 가능한가 — 실측

| 단계 | 재료 | 계산 가능 | 실측 |

| 5 | `spar_sessions.level` + `belt_history` | ⚠️ 조건부 | **20건** 해당 (아래 함정 주의) |

`classes.theme`는 자유 텍스트(예: `싱글엑스 가드 -> 50대50`)라 1단계 자동 판정의 신뢰할 재료가 아니다.
**1단계는 `drills.tech`를 주 재료로 삼고, `classes.theme`는 보조로만 쓴다.**

### 5.3 🔴 5단계의 함정 — 벨트 서열이 DB에 없고 표기가 섞여 있다

- `spar_sessions.level` (varchar(20)) 실제 값: `화이트` 24 · `블루` 13 · `퍼플` 9 · `블랙` 7 · 빈값 1 — **전부 한글**
- 본인 벨트 출처는 `belt_history` (`profile`에는 벨트 컬럼이 없다). 실제 값:

  | achieved_date | belt |
  |---|---|
  | 2025-07-15 | `white` |
  | 2025-09-19 | `white` |
  | 2025-12-19 | `white` |
  | 2026-05-25 | `화이트` |
  | 2026-08-07 | `블루` |

  **영문과 한글이 섞여 있다.** 2026-05-25를 기점으로 표기가 바뀌었다.

- **벨트 서열 정보는 DB 어디에도 없다.** 코드에 순서 맵을 정의해야 한다.

확정 결정 §5는 "용어는 도장 말(한글)로 확정"이다. 그 지시를 그대로 따라 **한글 키만으로 서열 맵을 짜면**:

| 서열 맵 | 5단계 판정 건수 | 판정 불가로 누락 |
|---|---:|---:|
| 영문+한글 병기 | **20건** | 0건 |
| **한글만** | **6건** | **34건** |

> 🔴 **한글만 매핑하면 20건이 6건으로 줄고, 14건이 에러 없이 사라진다.**
> NFD 때와 정확히 같은 실패 방식이다 — 예외가 아니라 "대상 아님"으로 조용히 걸러진다.

**필수 구현 규칙**:

```js
// 벨트 서열 — belt_history 에 영문·한글이 섞여 있으므로 양쪽 다 매핑해야 한다.
// 한글만 매핑하면 2026-05-25 이전 기록(영문 'white')이 조용히 판정에서 빠진다.
const BELT_RANK = {
  white: 0, '화이트': 0,
  blue:  1, '블루':   1,
  purple:2, '퍼플':   2,
  brown: 3, '브라운': 3,
  black: 4, '블랙':   4,
};
```

- 조회 시 매핑에 **없는 값을 만나면 조용히 건너뛰지 말고 로그를 남긴다**(새 표기 유입 감지).
- **"본인 벨트"는 현재 벨트가 아니라 그 스파링 날짜 시점의 벨트다.**
  `belt_history`에서 `achieved_date <= spar_days.date`인 마지막 행을 쓴다.
  현재 벨트(블루=1)로 전 기간을 판정하면 **20건이 10건으로 줄어 절반이 조용히 사라진다**
  — 상대 레벨이 퍼플(2)·블랙(4)인 항목만 남고, 화이트(0)·블루(1)를 이겼던 과거 기록이 전부 빠진다.
  전멸이 아니라 **절반만 어긋나기 때문에** 숫자가 그럴듯해 보여 더 발견하기 어렵다.
- `spar_sessions`에는 날짜가 없다. 날짜는 `spar_days.date`에서 가져온다.
- `level` 빈값 1건은 "기록 없음"으로 처리한다.

## 6. 노드 7종 정의

연구(랩) 노드는 하나의 기술을 7개 관점으로 쪼개 기록한다. 노드는 `technique_id`로 기술을 참조만 하고,
사다리 상태를 자체 보유하지 않는다(§5.1).

| # | 노드 | 담는 것 | 예시 |
|---|---|---|---|
| 1 | **포지션** | 이 기술이 시작되는 자리 | 클로즈드 가드 · 사이드 컨트롤 |
| 2 | **그립** | 손·발로 잡는 지점과 순서 | 소매+깃 · 언더훅 |
| 3 | **세팅** | 걸기 전에 만들어야 하는 각도·거리·체중 배분 | 상대 팔 끌어 각도 만들기 |
| 4 | **엔트리** | 그 자리로 들어가는 진입 경로 | 니슬라이드로 패스 후 진입 |
| 5 | **리액션** | 상대가 보이는 반응 (막힌 이유의 원천) | 팔 숨김 · 프레임 세움 |
| 6 | **대처** | 그 리액션에 대한 내 답 | 팔 숨기면 오모플라타로 전환 |
| 7 | **피니시** | 마무리 동작 | 힙 올려 꺾기 |

설계 메모:

- **5(리액션)는 자동 유입 대상이다.** task-022에서 실패 항목마다 받는 "막힌 상대 리액션" 한 줄이
  이 노드로 흘러든다. 유입은 `technique_id` 매칭에 의존하므로 **§2.1의 49.4% 미매칭이 그대로 유입 손실률이 된다.**
- **1(포지션)과 7(피니시)의 분리는 §2.1 A유형(복합어)에 대한 "앞으로"의 해법이다.**
  `마운트 암바`를 하나의 기술명으로 만들지 말고, 포지션=`마운트` · 피니시=`암바`로 나눠 기록한다.
  그러면 `암바` 하나의 사다리에 마운트·오픈가드·스카프홀드 사례가 모두 모인다.
- 🔴 **다만 노드 모델은 A유형의 "정답"이 아니다 — 기존 문자열의 매칭 문제는 그대로 남는다.**
  노드는 **연구 화면에서 사람이 새로 입력하는 구조**일 뿐이어서, 이미 `spar_sessions.success`에
  문자열 `마운트 암바`로 적혀 있는 기존 기록을 `암바`에 붙여주지 않는다
  (`마운트 암바` vs `암바` = 토큰 {마운트,암바} ∩ {암바} → 자카드 **0.5**, fuzzy 임계 미달로 여전히 미매칭).
  **사다리 4·5단계와 위 리액션 자동 유입은 계속 기존 문자열 이름 매칭에 의존한다.** 즉 노드 모델은
  앞으로 쌓일 기록의 구조를 개선할 뿐, §2.1의 49.4% 미매칭을 해소하지 않는다 — 별도 과제로 다뤄야 한다.
- 7종은 **모두 선택 항목**이다. 비어 있어도 노드는 저장된다(확정 결정 §3의 "비워도 저장" 원칙 확장).

## 7. 이름 정규화 정책

### 7.1 기존 유틸 재사용 (신규 작성 금지)

| 파일 | 제공 | 용도 |
|---|---|---|
| `backend/src/utils/nfc.js` | `toNFC` · `arrToNFC` · `eqNFC` | NFC 정본화 (task-014) |
| `backend/src/utils/techMatch.js` | `normalize` · `tokenize` · `jaccard` · `matchTechnique` | 4단 결정적 매칭 (task-009) |
| `backend/src/utils/techAliases.js` | `TECH_ALIASES` (약 45개) | 별칭 사전 |

`techMatch.normalize()` = NFC + 소문자 + 공백·하이픈·중점(`-`·`·`·`ㆍ`·`・`) 제거.
`matchTechnique()`는 exact → alias → fuzzy(자카드 ≥ 0.75, 후보 유일할 때만) → none 순으로 판정하고,
**미매칭 시 자동 생성하지 않는다.** 이 안전장치는 유지한다.

### 7.2 현재 DB 정규화 상태

**NFD 잔존 0건** — `techniques.name`, `spar_sessions.success`의 기술명 모두 NFC다.
다만 `ytdlp`는 지금도 NFD를 반환하는 살아있는 유입원이므로 비교 시점 정규화(2층 방어)는 계속 필요하다.

네거티브 컨트롤(정규화를 끄면 숫자가 달라지는지 확인):

| 조건 | 완전 일치 |
|---|---:|
| 양쪽 NFC 정규화 | 14종 |
| 후보 트리만 NFD (정규화 실패 상황 재현) | **0종** |

정규화가 깨지면 매칭이 14→0으로 **전멸**한다. 현재 0건이라고 방어를 빼면 안 되는 이유다.

### 7.3 권고 (실행은 승인 후)

1. **`techAliases.js` 보강** — §2.1 B유형 6종 추가로 미매칭이 즉시 줄어든다. 코드만 고치면 되고 데이터 무변경이라 가장 안전하다.
2. **fuzzy `tokenize()` 비대칭 수정** — 토큰화 전에 `normalize()`와 같은 기준으로 공백을 정리해
   `보우앤애로우 쵸크`가 `보우 앤 애로우 쵸크`와 같게 취급되도록 한다.
3. **괄호 병기 제거를 정규화에 포함** — `키마라 (Kimura)` 계열. 단 이것만으로는 안 풀리는 항목이 다수다(§2.2).
4. **C유형(트리 누락)은 사용자에게 제안만** — 자동 생성 금지 원칙 유지.
5. **데이터 자체 수정은 오타 1건(`싱글렏 스윕`)만** 후보. 나머지는 코드로 흡수한다.

> 원칙: **데이터를 고치기 전에 매칭 코드로 흡수할 수 있는지 먼저 본다.**
> 데이터 수정은 되돌리기 어렵고, 4개 저장소 전파 문제를 다시 부른다.
